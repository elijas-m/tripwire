# Разметка эпизодов для калибровки

Датасет служит для измерения lead-time, precision/recall и Brier score вне
курированного PIT-корпуса. Пилот проверяет словарь и процесс разметки; для
калибровки нужны ≥100 меток и ≥20 позитивов на горизонт.

Текущая версия схемы — **2** (2026-11-01). Пилот в `pilot/` размечен по v1;
M2 использует v2. Изменения v2: субъект определяется на уровне эпизода,
разведены `non_material` и `out_of_scope`, для кинетики допускается tier 2
при явных правилах уверенности, открытые окна помечаются как временные.

## Охват

Только геополитические театры: `EU_RU`, `ISRAEL`, `GULF`, `MENA`. События
`NATURE`, `PANDEMIC` и `MARKETS` в датасет не входят: у них другой тип исхода
(мгновенное событие, вспышка, рыночная аномалия), и общий lead-time для них
некорректен.

## Единица разметки

Метка ставится на **кластер-эпизод** — кластер (`clusters.id`) в его первом
состоянии, когда система его заметила. Один кластер даёт одну метку; серия
дублей и ревизий не создаёт новых эпизодов.

`candidate_id` имеет вид `cluster:<id>@<first_seen>` и стабилен между
экспортами. `first_seen` — начало наблюдения по данным системы. Время
фактического решения системы (`alerts.decided_at`) в слепом файле скрыто: оно
нужно для lead-time и лежит в `sealed.jsonl`.

## Субъект

Исход засчитывается только если он относится к тому же субъекту, что и
кластер: страна/актор, о котором шла речь. Эскалация в том же театре, но с
другим субъектом, позитивом не считается.

`subject` записывается как `{"country": "<ISO2>", "actor": "<имя или пусто>"}`.
Если субъект неоднозначен, ставится `confidence: low`, и метка не идёт в
калибровку. Если театр кластера и субъект расходятся (например, событие в
Ормузском проливе попало в `EU_RU`), ставится `in_scope: false`; такая метка
остаётся для аудита, но исключается из метрик. `in_scope` описывает только
совпадение субъекта с театром и не отменяет проверку содержания эпизода.

### Уровень эпизода

Субъект сравнивается на уровне эпизода: страна/актор **и** конкретная
ситуация — цель, объект, локация. Исходом считается материальное развитие
именно этой ситуации, а не любое событие той же страны. В идущей войне
эскалация в любой точке страны иначе тривиально превращает почти каждый
кластер в позитив, а случайные негативы — в позитивы.

| Якорь | Кандидат в исход | Позитив? |
|---|---|---|
| Удар по Виннице | Повторный удар по Виннице через 12 ч | да |
| Удар по Виннице | Удар по Харькову через 12 ч | нет, другой эпизод |
| Заявление о готовности группировки | Развёртывание той же группировки | да |
| Заявление о готовности | Кинетика на другом направлении | нет |

Если связь между якорем и событием спорная, ставится `confidence: medium`,
а сомнительная — `low`.

## Тип случая

`case_type` отделяет упреждающий прогноз от обнаружения и шума:

| `case_type` | Значение |
|---|---|
| `anticipatory` | материальное развитие той же ситуации произошло после якоря в пределах горизонта |
| `detection` | материальное событие той же ситуации уже было на момент якоря, нового после него нет |
| `non_material` | риторика, политика, бюджет, заявления по безопасности или внешней политике — без материального действия |
| `out_of_scope` | эпизод не про геополитическую безопасность (быт, культура, спорт, внутренняя социальная политика) либо субъект не соответствует театру |
| `unresolved` | исход нельзя проверить: окно ещё не закрыто или данные противоречивы |

Калибровка и lead-time считаются только по `anticipatory` с `in_scope: true` и
`confidence != low`. `detection` показывает, что система узнала событие уже
после его начала. `non_material` и `out_of_scope` — кандидаты в ложные тревоги,
если по ним был алерт.

### Границы типов

Проверяйте в таком порядке:

1. `in_scope: false` (субъект и театр расходятся) → `out_of_scope`.
2. Эпизод вообще не про безопасность — быт, культура, спорт, внутренняя
   социальная политика → `out_of_scope`.
3. Материальное событие той же ситуации уже было на якоре, нового нет →
   `detection`.
4. После якоря появилось материальное развитие той же ситуации →
   `anticipatory` (приоритет выше `detection`, если событие новое).
5. Есть только заявления, встречи, бюджет или политика по безопасности и
   внешней политике → `non_material`.
6. Проверить нельзя → `unresolved`.

Бытовое и культурное отличается от `non_material` по предмету, а не по
масштабу: заявление министра здравоохранения о достижениях медицины —
`out_of_scope`, заявление о готовности применить силу — `non_material`.
Спорный случай, который не меняет негатив на позитив, не требует новой
метки; если меняет — `confidence: medium` и объяснение в `notes`.

## Шкала исхода

| `outcome_severity` | Значение |
|---|---|
| 0 | эскалации нет |
| 1 | только риторика, угрозы, заявления |
| 2 | развёртывание, мобилизация, официальный приказ, закрытие пространства |
| 3 | кинетика: удар, перехват, боестолкновение |
| 4 | стратегическое: война, массовые жертвы, применение ОМП |

Основной позитив — `severity >= 2`. Строгий вариант — `severity >= 3`;
отчётность считается для обоих порогов, словарь метки от порога не зависит.
Риторика (`1`) всегда негатив.

`outcome_type`: `none`, `rhetoric`, `posture`, `kinetic`, `strategic`.

## Горизонты

Метка хранит один `outcome_at` — время первого подтверждённого события нужной
тяжести **после** якоря наблюдения. Исход должен произойти строго позже
`first_seen`: событие, которое уже произошло до того, как система его увидела,
не является исходом прогноза. Такие случаи относятся к обнаружению, а не к
lead-time.

```
y24  = first_seen < outcome_at <= first_seen + 24h
y72  = first_seen < outcome_at <= first_seen + 72h
y168 = first_seen < outcome_at <= first_seen + 168h
```

При расчёте lead-time окно сдвигается на `decision_at` из закрытого файла:
`y72 = decision_at < outcome_at <= decision_at + 72h`. Поэтому разметчик
записывает только `outcome_at`, `first_seen` служит слепым якорем.

Основной горизонт — 72 часа. Негатив валиден только если
`observed_until >= first_seen + 72h`; иначе метка получает
`outcome: null` / `unresolved` и исключается из метрик. Для `y168` требуется
покрытие 7 дней.

### Временные метки

Если тип уже однозначен по содержанию (бытовое событие, обнаружение,
риторика), метку можно поставить до закрытия 72 часов, но она **временная**:
`observed_until` — фактическое время проверки, а не конец горизонта.
К моменту `first_seen + 72h` нужно либо выпустить новую версию с обновлённым
`observed_until` (если материала не появилось), либо `supersedes` с
`anticipatory`, если материал появился. Калибровка отбрасывает непокрытые
горизонты, поэтому без обновления такой негатив в Brier не попадёт.

Для `anticipatory` покрытие не требуется: достаточно, чтобы `outcome_at`
попадал в горизонт. Поздние события после `outcome_at` метку не меняют.

## Поля метки

| Поле | Описание |
|---|---|
| `label_id` | `L<YYYY-MM>-<NNNN>` в пилоте; шаблон M2 подставляет `cluster_id` (`L<YYYY-MM>-<101>`). Уникален и не меняется |
| `candidate_id` | связь со слепым кандидатом |
| `cluster_id` | кластер из `clusters` |
| `theater` | `EU_RU`, `ISRAEL`, `GULF`, `MENA` |
| `subject` | страна/актор, к которому относится исход |
| `in_scope` | `true`, если субъект и театр соответствуют друг другу |
| `decision_at` | из закрытого файла, не из слепого |
| `case_type` | `anticipatory`/`detection`/`non_material`/`out_of_scope`/`unresolved` |
| `outcome` | 1/0 для `anticipatory`; `null` для остальных типов |
| `outcome_type` | `none`/`rhetoric`/`posture`/`kinetic`/`strategic` |
| `outcome_severity` | 0–4 |
| `outcome_at` | время первого подтверждённого события |
| `observed_until` | докуда проверено отсутствие исхода |
| `evidence` | список `{url, publisher, tier}` |
| `confidence` | `high`/`medium`/`low` |
| `annotator` | кто размечал |
| `labeled_at` | время разметки |
| `supersedes` | `label_id` исправляемой метки или `null` |
| `notes` | свободный комментарий, без секретов и персональных данных |

## Доказательства

- Базово — первичные или tier 0/1 источники: официальные заявления, агентства,
  профильные мониторинги.
- Для кинетического исхода допускаются именованные агентства и профильные медиа
  tier 2 (РИА, Укринформ, Fakty ICTV, Censor.NET и аналогичные). Tier
  фиксируется в `evidence`; собственный алерт Tripwire источником не является.
- Уверенность для кинетики:
  - `high` — tier 0/1 или ≥2 независимых origin-домена tier 2;
  - `medium` — один tier-2 источник;
  - `low` — сомнение в самом событии или субъекте. Tier 2 сам по себе не
    понижает уверенность до `low`.
- GDELT используется как поисковый экран, UCDP GED — как ретроспективная
  сверка. Ни один из них не является единственным подтверждением.
- Собственные алерты и скоры Tripwire доказательством исхода не считаются.
- В метку попадают только публичные URL; секреты, токены и персональные
  данные не сохраняются.

## Слепая разметка

`candidates.jsonl` не содержит балла, уровня, страты и времени решения.
`sealed.jsonl` с этими полями лежит отдельно и не показывается разметчику до
фиксации его меток. Разметчик видит текст событий, ссылки, театр и даты
публикации.

Пилот: 20 кандидатов (2 алерта, 9 near-miss, 9 случайных негативов). Два
разметчика работают независимо; согласие считается по Cohen's kappa на
`case_type`. Цель — kappa ≥ 0.7. При меньшем значении правится словарь, а не
метки.

## Выборка

- `alert` — все эпизоды с алертом уровня ≥ WARNING (в геополитике сейчас 2).
- `precursor` — кластеры, чьё первое событие пришло от прекурсорного источника
  (`easa_czib`, travel advisories, `ukmto_jina`, Tzeva). Именно они дают
  упреждающие случаи; без отдельной страты они тонут в случайной выборке.
- `near_miss` — кластеры с баллом в диапазоне `[4, 8)` без алерта ≥ WARNING.
- `random` — детерминированная выборка кластеров с баллом ниже 4; нужна для
  оценки базовой частоты и ложных тревог.

Эпизоды не дублируются между стратами: приоритет `alert` → `precursor` →
`random` → `near_miss`.

Случайная выборка обязательна: если размечать только алерты и near-miss,
получится смещение отбора и калибровка будет завышена. Курированные
PIT-сценарии в калибровку не входят — они отобраны по факту эскалации.

## Метрики

- **Lead-time** = `outcome_at - decision_at` для истинно положительных
  эпизодов; медиана, IQR, P10/P90 по театрам и tripwire.
- **Precision/recall** на уровне эпизодов: TP — эскалация с решением до
  `outcome_at`; FN — эскалация без решения; FP — решение без исхода за 72 ч.
- **Brier** = `mean((p_i - y_i)^2)`, где `p_i` — калиброванная вероятность из
  балла на якоре: `clusters.score_initial`, зафиксированного после первого
  события кластера. Финальный `clusters.total_score` не используется — он
  растёт с последующими событиями и заносит будущее в прогноз.
- **Brier skill score** = `1 - Brier / Brier_base`, базовая вероятность — из
  train-части.
- Доверительные интервалы — bootstrap по кластерам и по дням (1000 ресэмплов).
- Brier публикуется только при N ≥ 100 и ≥ 20 позитивах на горизонт. До этого
  печатается «недостаточно данных», а отчётность ограничивается lead-time и
  precision/recall.
- Хронологический split 60/40 по `first_seen` — тому же якорю, к которому
  привязан исход. Метрики и горизонт фиксируются до просмотра тестовой части.

## Калибровка M2

Расчёт:

```
python -m tripwire --calibrate-labels --calibration-dir <каталог> \
  --calibration-json <каталог>/calibration.json
```

- Позитив — `anticipatory` с `first_seen < outcome_at ≤ first_seen + h`.
- Негатив — `detection`/`non_material`/`out_of_scope`, если `observed_until`
  покрывает горизонт; иначе `y` неизвестен и эпизод выпадает из этого
  горизонта.
- Исключаются: `unresolved`, `confidence: low`, `in_scope: false`, метки без
  `outcome_at` у `anticipatory`, метки без якорного балла.
- Модели: isotonic (основная) и Platt (справочно), обучение только на
  train-части. Отчёт даёт Brier, базу, skill и 95% CI по кластерам и дням.
- Строки без якорного балла — эпизоды, увиденные до внедрения фиксации
  `score_initial`. Они годятся для lead-time, но не для Brier; для M2 нужны
  эпизоды, `first_seen` которых позже даты развёртывания фиксации.
- Цель M2: ≥100 размеченных эпизодов и ≥20 позитивов на горизонт, из них
  случайные негативы обязательны. Экспорт запускается с двумя фильтрами:
  `--labels-require-anchor` оставляет только кластеры с зафиксированным
  `score_initial`, `--labels-min-age-hours 72` — только эпизоды с закрытым
  основным горизонтом. Каждый раунд пишется в каталог с датой; повторный
  запуск в тот же каталог запрещён, поэтому `--labels-force` в недельном
  цикле не используется. Пример:

```
python -m tripwire --export-labels --labels-out backtest/labels/m2/2026-11-04 \
  --labels-since-days 365 --labels-negatives 15 --labels-precursor 30 \
  --labels-near-miss 50 --labels-require-anchor --labels-min-age-hours 72 \
  --labels-exclude backtest/labels/m2
```

- Вместе с кандидатами экспорт пишет `labels.template.jsonl` — по строке на
  кандидата с `case_type: null` и `label_id = L<YYYY-MM>-<cluster_id>`. Шаблон
  только заготовка: завершённой меткой считается строка в `labels.jsonl` с
  заполненным `case_type`.
- `--labels-exclude` — реестр уже размеченных эпизодов. Принимает файл или
  каталог; каталоги сканируются по `labels.jsonl`, поэтому шаблоны и черновики
  (`labels.agent.jsonl`) эпизод не закрывают. Исключение идёт и по
  `candidate_id`, и по `cluster_id`, то есть один кластер даёт одну метку.
  `--labels-since-days 365` при этом безопасен: недельный раунд — это дифф
  против реестра, а не повторная выборка. Несуществующий путь — ошибка, а не
  молчаливое отсутствие фильтра.
- Перед калибровкой раунды склеиваются в один каталог:

```
python -m tripwire --merge-labels --labels-merge-root backtest/labels/m2 \
  --labels-merge-out backtest/labels/m2/aggregate
python -m tripwire --calibrate-labels \
  --calibration-dir backtest/labels/m2/aggregate \
  --calibration-json backtest/labels/m2/aggregate/calibration.json
```

- `--merge-labels` применяет `supersedes` (остаётся текущая версия метки),
  дедуплицирует `sealed.jsonl` (предпочитая строку с непустым
  `score_initial`), пропускает неполные метки и сообщает конфликты. `aggregate/`
  исключается из повторного сканирования, поэтому слияние идемпотентно.
- Якорный балл пишется только с 2026-10-31T23:15Z. Эпизоды раньше этой даты
  годятся для lead-time, но не для Brier; фильтр `--labels-require-anchor`
  исключает их из M2.
- `--labels-min-age-hours 72` исключает открытые окна, поэтому метки M2 не
  требуют последующего обновления `observed_until`. Ритм — один раунд в
  неделю: `m2/2026-11-04`, `m2/2026-11-11`, …
- Страта прекурсоров и near-miss ускоряют набор позитивов, но не отменяют
  случайную выборку: без неё базовая частота и калибровка завышены.

## Исправления

Метки не перезаписываются. Исправление — новая строка с новым `label_id` и
`supersedes: <старый label_id>`. При анализе используется последняя версия по
цепочке `supersedes`.

## Файлы

Раунд — каталог с датой (`m2/2026-11-04`):

- `candidates.jsonl` — слепые кандидаты для разметки.
- `labels.template.jsonl` — заготовки меток: по строке на кандидата,
  `case_type: null`, `label_id = L<YYYY-MM>-<cluster_id>`.
- `sealed.jsonl` — `candidate_id` → страта, якорный балл `score_initial`,
  финальный балл, уровень, `decision_at`. Хранится локально и не публикуется
  до завершения разметки.
- `labels.jsonl` — заполненные метки; единственный файл, который считается
  реестром завершённых меток.
- `manifest.json` — параметры экспорта: период, seed, фильтры `require_anchor`,
  `min_age_hours`, `exclude_paths`, счётчики, версия схемы.

Сводка — `m2/aggregate/` (создаётся `--merge-labels`):

- `labels.jsonl`, `sealed.jsonl` — склеенные раунды с разрешёнными
  `supersedes`.
- `manifest.json` — список раундов, пропущенные неполные метки, конфликты
  меток и `sealed`, строки без пары.
- `calibration.json` — Brier, skill, разбивка train/test и доверительные
  интервалы по горизонтам (создаётся `--calibrate-labels`).

Схема версионируется полем `schema_version`; несовместимое изменение схемы
требует новой версии и переразметки затронутых полей.

История:

- **v1** — пилот 2026-11-01, 20 эпизодов; субъект на уровне страны.
- **v2** — 2026-11-01: субъект на уровне эпизода, границы
  `non_material`/`out_of_scope`, tier 2 для кинетики, временные метки открытых
  окон. Поля метки не изменились; меняется трактовка. Переразметка нужна только
  спорным эпизодам, у которых меняется `case_type`.
